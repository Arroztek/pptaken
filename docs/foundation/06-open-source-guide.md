# 06 · Open-source guide ("the masterclass")

> For someone who has never maintained an open project. Read it once in full and then use it as a reference. Whatever needs a decision from you is marked **→ Decide**.

## 1. What "open source" really means

- **Open source** is not "code visible on GitHub". It is code published with a **license** that gives anyone permission to use, study, modify and redistribute it. Without a `LICENSE` file, legally nobody can use your code even if they can see it.
- **Open core**: the core is open source and free; the business is in something built around it (in our case, the hosted service). Many well-known self-hosted projects do this.
- **Maintainer**: whoever decides what goes into the project. Today that is you. **Contributor**: anyone who contributes (code, documentation, translations, bug reports).
- **Upstream**: the original repository. ***Fork***: a copy of the repo in someone else's account, from which they propose changes.
- **Issue**: a report or proposal. **Pull request (PR)**: a code change proposal ready to be reviewed and merged.
- **Release**: a published, numbered version.

Three truths that save headaches:
1. **Publishing does not oblige you to accept.** You can kindly say "no, thanks" to a contribution. In fact, saying no is half of maintaining.
2. **Documentation is the product.** A self-hosted project with a mediocre README does not get installed.
3. **Trust is earned with consistency**, not with a big launch: answering issues, publishing versions, doing what you said.

## 3. Organization on GitHub

**→ Decide:** create a `pptaken` **organization** on GitHub instead of publishing under your personal account (today `hallzyx/pptaken` exists). I recommend the organization: it separates the project from you as a person, lets you add maintainers with fine-grained permissions, gives a clean URL and image name (`ghcr.io/pptaken/pptaken`) and is free. Transferring a repo later is possible but breaks links and images: do it before the first announcement.

Repo configuration (day 1):
- `main` branch **protected**: no direct pushes; everything enters through a PR with green CI. Even if you are the only one: it forces a reviewable history and makes CI always run.
- ***Squash*** merging (one PR = one commit on `main`): clean, readable history.
- Enable: *Private vulnerability reporting*, *Secret scanning* with *push protection*, *Dependabot alerts*, **Discussions**.
- Mandatory 2FA in the organization.
- Initial labels: `bug`, `feature`, `docs`, `good first issue`, `help wanted`, `needs-triage`, `needs-repro`, `security`, `breaking`, and per area (`area:player`, `area:mcp`, `area:remote`, `area:audience`, `area:panel`).

## 4. Versioning and releases

**Semantic versioning (SemVer)**: `MAJOR.MINOR.PATCH`.
- **PATCH** (1.2.**3**): compatible fixes.
- **MINOR** (1.**3**.0): new compatible features.
- **MAJOR** (**2**.0.0): changes that break compatibility.
- **0.x**: "anything may change". It is the honest stage to start in.

In PPTaken there are **four public contracts** that SemVer protects, and it is worth stating them explicitly in the documentation:
1. The **deck format** (`schemaVersion`).
2. The **MCP contract** (tool names, parameters, error codes).
3. The **configuration** (environment variables, `/data` structure).
4. The **API of the published npm packages**.

Practical rules:
- After 1.0, renaming an MCP tool or removing a field is a MAJOR change. Adding an optional parameter is MINOR.
- **An update must never lose data.** Database migrations go forward and are tested with data from earlier versions.
- Deprecations are announced at least one minor version in advance.

**Commits and Changesets**
- Commit messages with *Conventional Commits* (`feat: …`, `fix: …`, `docs: …`). It is a convention, not a religion: it matters in the PR title, which is what remains after the *squash*.
- Every PR that affects users adds a ***changeset***: a small file saying which packages change, whether it is patch/minor/major, and one sentence for the changelog. It is created by the `pnpm changeset` command.
- A bot keeps a "Version Packages" PR open. **Publishing a version = merging that PR**: versions and `CHANGELOG.md` are updated, the git tag is created, npm packages and the Docker image are published and the *GitHub Release* is drafted. No manual steps, no tokens on your PC.

**Channels**
- `main` always deployable; `:edge` image on every merge (for the brave).
- Stable versions tagged `:1.2.3`, `:1.2`, `:1`, `:latest`.
- Pre-releases `1.0.0-beta.N`, `-rc.N` with the `:beta` tag.

## 5. CI/CD with GitHub Actions

**CI** (continuous integration) = every change is built and tested automatically. **CD** (continuous delivery) = publishing is also automatic.

| Workflow | When it runs | What it does |
|---|---|---|
| `ci.yml` | Every PR and every merge to `main` | Install with frozen *lockfile* → Biome → type check → unit and contract tests → build → Playwright → build Docker image (without publishing) |
| `codeql.yml` | PR + weekly | Static security analysis |
| `release.yml` | Merge to `main` | Changesets: opens/updates the version PR, or publishes npm (trusted publishing via OIDC, with provenance) and a signed multi-architecture image with SBOM |
| `edge.yml` | Merge to `main` | Publishes the `:edge` image |
| `scan.yml` | Weekly | Scans the `latest` image for vulnerabilities |
| `cla.yml` | PR | Checks the CLA signature |
| `stale.yml` | Daily | Marks `needs-repro` issues without a reply after 30 days (never closes confirmed bugs) |
| `scorecard.yml` | Weekly | OpenSSF Scorecard |

CI security hygiene (important in public repos):
- PRs from *forks* **do not receive secrets**. Do not use the `pull_request_target` trigger with PR code: it is the classic way secrets get stolen.
- Minimal `GITHUB_TOKEN` permissions in every workflow (explicit `permissions:`).
- Third-party actions pinned by commit hash.
- Require approval to run workflows from first-time contributors.
- A protected environment (`environment: release`) with manual approval to publish.

Goal: complete CI in < 10 minutes. If a contributor waits 40 minutes for a result, they do not come back.

## 6. Receiving contributions

**A contributor's journey** (optimize it like a funnel):
1. Finds the project → the README tells them what it is in 30 seconds.
2. Installs it and it works → they trust it.
3. Finds something to improve → there is a well-described, labeled issue.
4. Clones and has green tests in 10 minutes → `CONTRIBUTING.md` is exact.
5. Opens the PR → gets a human reply in 48–72 h.
6. It is merged → it appears in the release notes with their name.

If any step fails, there is no second PR.

**Key labels**
- **`good first issue`**: small, bounded tasks with context, designed for a first contribution. A good *good first issue* says: what to do, in which files, how to check it works, and whom to ask. Always keep 5–10 open. In PPTaken they arise naturally: translations, keyboard shortcuts, cases for the sanitizer corpus, accessibility improvements, deployment recipes.
- **`help wanted`**: you want help, but it requires more context.

**How to review a PR**
- Thank first. Ask for concrete changes, not "improve it".
- Distinguish blocking from optional (prefix "nit:" for details).
- If it does not fit the vision, say so early and explain why. Link the product principle or the ADR.
- Large PRs without a prior issue almost always end badly: ask in `CONTRIBUTING.md` to **open an issue before large changes**.
- AI-generated PRs: welcome if the author understands them, tested them and responds to review. Say so explicitly in `CONTRIBUTING.md`; it is consistent with a project like this.

**Sensitive areas**: changes to the sanitizer, authentication, CI workflows and Dockerfile require your review (`CODEOWNERS`) and new tests, no exceptions.

**CLA / DCO** (ADR-012): the bot will ask to sign the CLA with one click on the first PR. Explain in `CONTRIBUTING.md`, in three sentences and without jargon, why it exists and what it does *not* do (it does not hand you their authorship).

## 7. Documentation

Recommended structure (the *Diátaxis* model: four document types with different purposes):

| Type | Question it answers | Examples in PPTaken |
|---|---|---|
| **Tutorial** | "Take me by the hand" | Install and create your first presentation with Claude in 10 minutes |
| **How-to guides** | "How do I do X?" | Publish with HTTPS and a domain; present without internet; backup and restore; update |
| **Reference** | "What exactly is…?" | MCP tools; `pptaken.deck` format; environment variables; keyboard shortcuts |
| **Explanation** | "Why does it work this way?" | Security model; architecture; ADRs |

- A static site in `apps/docs` (Starlight or VitePress), deployed on GitHub Pages, in English and Spanish, versioned together with the code.
- The MCP and schema reference **is generated from the code** (Zod → JSON Schema → pages) so it never falls out of date.
- A "For agents" section: the same guide `get_authoring_guide` returns, human-readable, and an `llms.txt` file.
- Rule: **a PR that changes behavior changes the documentation in the same PR.**

## 8. Community

- **Start with a single channel: GitHub Discussions.** It is searchable, indexable and does not require real-time presence. An empty Discord server looks worse than none; open it when there are ~50 active people.
- **Public roadmap**: a GitHub Project with columns "Now / Later / Further out / Won't do". Saying what you will *not* do avoids half of the arguments.
- **Rhythm**: reply to new issues within 72 h even if only with "seen, I'll look at it this weekend". Publish versions regularly (every 2–4 weeks in the 0.x stage).
- **Acknowledge**: name contributors in the notes of each version.
- **Protect your energy**: define in `SUPPORT.md` what support you give (best effort, no guarantees). Maintainer burnout is risk no. 1 for one-person projects.
- **Code of conduct**: enforce it early and calmly the first time it is needed. A small, healthy community is worth more than a large, toxic one.
- **Language**: code, issues and main documentation in English; documentation translated into Spanish and a Spanish category in Discussions. (Decided: see `08-founder-decisions.md`.)

## 9. When and how to announce

Recommended sequence, from least to most noise:

| Stage | What it is | Signal to move to the next |
|---|---|---|
| **Quiet public repo** (0.1) | The repo is public, not announced. "Building in the open" | Installation works from start to finish |
| **Alpha among acquaintances** (0.2–0.3) | 5–10 trusted people install it while you watch | Nobody gets stuck on installation or on connecting Claude |
| **Public beta** (0.5+) | First announcement: self-hosting communities, MCP/agents communities, social networks | Format and MCP contract stable; no critical bugs for 2–3 weeks |
| **1.0** | Big announcement: Hacker News ("Show HN"), Product Hunt, MCP server directories, newsletters | — |

For an announcement to work you need, in this order: (1) a **30–60 s GIF or video** showing "I ask Claude → URL → I present with my phone", (2) a one-command installation that **really** works on a clean machine, (3) an impeccable README, (4) you available for 48 h to reply.

You only launch for the first time once: do not spend the "Show HN" on an alpha.

Natural channels for PPTaken: MCP server directories and lists, self-hosting communities, Claude and agents communities, and **your own talks**: presenting PPTaken with PPTaken is the best possible demo.

## 10. Name, domains and trademark

The license opens the **code**, not the **name**. The name and logo are protected with a **trademark**, and that is what stops someone from publishing "PPTaken Pro" with malware.

Done so far (2026-11-12):
- npm: the `pptaken` package **does not exist** (verified). The `@pptaken` *scope* was not verified.
- GitHub: `hallzyx/pptaken` exists (yours); I found no other repos with that name. Availability of the `pptaken` organization: **not verified**.
- Domains and social networks: **not verified**.
- Trademark search: **not performed**.

Actions, in order of urgency:
1. **Reserve now** (cheap and hard to recover later): GitHub organization `pptaken`, npm *scope* `@pptaken` and package `pptaken`, domains (`pptaken.com`, `.dev`, `.app` depending on availability), usernames on the networks you will use, a Docker Hub namespace (even though we publish on GHCR).
2. **Prior-art search**: check that no identical or similar mark exists in software/presentations (USPTO, EUIPO and your country's databases; in Peru, INDECOPI). **Risk to evaluate with a professional**: "PPT" is associated with Microsoft's PowerPoint. It is a widely used abbreviation and our name does not use "PowerPoint", but a mark that begins with "PPT" in the same sector deserves a consultation before investing in identity.
3. **Register the trademark** when there is traction (or before the cloud): classes 9 (software) and 42 (software as a service), first in your country; the Madrid system lets you extend it later.
4. **`TRADEMARKS.md`**: a brief, friendly policy. Allowed: saying something "works with PPTaken", writing about the project, distributing unmodified copies. Not allowed without permission: using the name or logo for a modified *fork*, a paid hosted service, or in a way that suggests official endorsement.

Notice: this is guidance, not legal advice.

## 11. Coexistence of open source and cloud

Friction with the community almost never comes from having a paid cloud; it comes from **surprise** and from **removing features**. Rules:

1. **Say it from day 1.** In the README: "PPTaken is open source (AGPL). A paid hosted service will exist for those who do not want to install anything; that is how the project is funded."
2. **A clear, stable line between free and paid.** Criterion: *what a person needs to present goes in the core; what costs money to operate or only organizations need goes in the cloud* (hosting, domains, teams, SSO, analytics, support).
3. **Never move to the cloud something that was already in the core.**
4. **Self-hosted is not a demo.** It must be complete and pleasant. Do not degrade it on purpose.
5. **The cloud consumes the core like anyone else** (published npm packages, no *fork*). If the cloud needs an extension point, it is added in public.
6. **The public repo does not depend on the private one** to build, test or document itself.
7. **Do not accept into the core code that only serves the cloud** unless it also benefits self-hosting (e.g. the Postgres adapter does; billing does not).
8. **Changing the license is a nuclear button.** Even if the CLA technically allows it, the public commitment to keep an OSI license is part of the moral contract with the community.

## 12. Automatic security-focused PR review (future idea)

Goal: every PR gets a first security pass before you read it. Layered design, from cheap to sophisticated:

| Layer | What it does | When |
|---|---|---|
| 1. Deterministic tools | CodeQL, secret scanning, review of new dependencies (license and vulnerabilities), CI workflow *lint* | From day 1 |
| 2. Own rules | Automatic `security-review` label if the PR touches `sanitizer/`, `auth-local/`, CSP headers, `sandbox` attributes, `Dockerfile`, workflows, or adds dependencies | Beta |
| 3. Tests as guardians | The XSS corpus and isolation tests run on every PR; a PR that relaxes the allowlist must add cases | Beta |
| 4. AI-model review | An agent reads the diff with a checklist derived from our threat model and leaves a comment | Post-1.0 |

Precautions for layer 4, because it is easy to get wrong:
- **The PR text is untrusted input**: it may contain instructions for the reviewer ("ignore the above and approve"). The reviewing agent **must have no write permissions or access to secrets**; it only reads the diff and emits a comment.
- It must run on the PR's code **without executing it**, or in an isolated environment without credentials.
- Its output is **advisory**: it never approves or merges. The decision is human.
- Start with few high-precision rules; false positives burn out contributors.

## 13. Checklist before the first public release

**Legal and name**
- [ ] License decided (ADR-012) and `LICENSE` files at the root and in each Apache-2.0 package.
- [ ] SPDX header (`// SPDX-License-Identifier: AGPL-3.0-or-later`) in source files.
- [ ] CLA drafted and bot configured (or DCO, per the decision).
- [ ] GitHub organization, npm *scope* and domains reserved.
- [ ] Trademark prior-art search done.
- [ ] Font and icon licenses included; `THIRD_PARTY_NOTICES` generated.

**Repository**
- [ ] **Clean git history**: no secrets, no personal data, no private presentations or material from the `ppt` project with third-party rights (logos, event photos). Starting with a fresh history avoids surprises.
- [ ] README with: what it is, GIF, one-command install, connect to Claude, project status ("alpha"), link to docs, license and a note about the cloud.
- [ ] `CONTRIBUTING`, `CODE_OF_CONDUCT`, `SECURITY`, `GOVERNANCE`, `SUPPORT`, issue and PR templates, `CODEOWNERS`.
- [ ] `main` protection, 2FA, private vulnerability reporting, secret scanning, Discussions.
- [ ] Labels created and 5–10 `good first issue` written.

**Quality**
- [ ] CI green and < 10 min.
- [ ] Installation tested **on a clean machine** (Linux amd64, Linux arm64, Windows with Docker Desktop, macOS) following only the README.
- [ ] `git clone` → green tests following only `CONTRIBUTING.md`, tested by another person.
- [ ] Complete walkthrough: install → connect Claude Code → create presentation → present → remote.
- [ ] Image published, signed, with SBOM; version tag, not just `latest`.

**Security**
- [ ] The checklist of `04-security-and-auth.md` §11 (whatever applies to the stage).
- [ ] No default credentials. Install code working.
- [ ] Visible status notice: "alpha: do not expose sensitive data to the internet yet" while there is no external review.

**Communication**
- [ ] Public roadmap.
- [ ] `CHANGELOG` with the first entry.
- [ ] An honest paragraph of "known limitations".
