# 01 · Product and scope

> PPTaken foundation document. Date: 2026-11-12. Status: CTO proposal for the founder's validation.

## 1. What it is (and what it is not)

**PPTaken is the stage, not the brush.** An AI agent (Claude or another) designs the slides and hands them over by MCP to the user's PPTaken instance; PPTaken returns a URL and, from there, takes care of everything that happens *during* the presentation: projecting, advancing, notes, clock, control from the phone, shareable link, quiz and audience questions.

| PPTaken IS | PPTaken is NOT |
|---|---|
| A server that receives presentations as **data** and runs them in the browser | A slide editor (it does not compete with PowerPoint, Canva, Google Slides) |
| An **MCP** server designed so an agent uses it correctly the first time | Its own AI slide generator (we call no LLM; the agent belongs to the user) |
| Presenter and audience tools | A video-conferencing or recording platform |
| Self-hosted, one container, no external dependencies | A SaaS (that will be `pptaken-cloud`, later) |

Positioning sentence: **"Your agent designs. You present."**

### Product principles (to break ties)

1. **Presenting never fails.** Once loaded, the presentation works without a network. Everything else (remote, audience) degrades gracefully.
2. **The agent gets it right the first time.** The MCP contract, the errors and the authoring guide are designed for an LLM, not for a human with the docs open.
3. **Secure by default.** The content is generated by a third party (the agent); it is always treated as untrusted.
4. **One command to install, one button to connect.**
5. **Few tools, done well.** We prefer cutting features over lowering the quality of the base.
6. **The player is neutral.** PPTaken's interface disappears when the show starts: the content is the protagonist.

## 2. Actors

| Actor | Who they are | How they authenticate | What they can do |
|---|---|---|---|
| **Owner** (administrator) | The person who installed or administers the instance. In v1 there is exactly one. | Password + session (cookie) | Everything: manage presentations, tokens, links, approve quizzes, present |
| **Agent** | Claude (or another MCP client) acting on the owner's behalf | API token or OAuth token issued by the instance, with *scopes* | Create/edit/list/delete presentations, upload assets, create quiz **drafts**. It **cannot** approve a quiz nor (by default) publish links |
| **Presenter** | Whoever is in front of the audience. Usually the owner; sometimes a third party with a link | Owner session, or delegated presenter link (v1.1) | Navigate, see notes, pair the phone, open/close audience tools |
| **Remote control** | The presenter's phone | QR pairing (one-time secret → device credential) | Next/previous, laser pointer, clock. It does not see or edit content outside that session |
| **Public-link viewer** | The organizer projecting, or anyone with the link | Read-only token in the URL | View and navigate the presentation. No notes, no panel, no audience |
| **Audience** | The public in the room | Anonymous, no account; ephemeral per-device identity | Answer the quiz, submit and vote on questions |

Key concept for the founder: **owner and agent are the same "legal person" but not the same actor**. The agent can make mistakes or be manipulated (prompt injection in a document it was handed). That is why some things can only be done by a human with a session: approving a quiz, creating a public link (by default), deleting permanently.

## 3. Main use cases

1. **"Make me a presentation"**: the owner asks Claude for a talk; Claude calls `create_presentation`; the owner receives a URL and opens it.
2. **Iterate**: "change slide 4, add a table" → `update_slides`; the owner reloads and sees the new revision.
3. **Present in the room with the phone as clicker**: open the URL on the laptop, press `R`, scan the QR, advance from the phone with a laser pointer.
4. **Present without internet**: the presentation was loaded earlier at the hotel; in the room there is no WiFi; the whole player works the same.
5. **"I don't have my laptop"**: the owner creates a public link and gives it to the organizer, who projects it from their machine. The owner controls from their phone (needs a network) or the organizer advances with the keyboard.
6. **Quiz at the end**: Claude proposes 8 questions (draft); the owner reviews and approves them in the panel; live, the audience joins with a QR, answers and sees the ranking.
7. **Anonymous questions**: during the talk the audience submits and votes on questions; at the end the presenter opens the most voted.
8. **Install and connect**: `docker compose up -d` → open the welcome page → create the password → "Connect to Claude".

## 4. Key user stories (with acceptance criteria)

**Installation and onboarding**
- H1. *As an owner, I want to start the server with a single command.* ✔ With Docker installed, one command leaves the server at `http://localhost:8080` in < 60 s on a 1 vCPU / 512 MB VPS.
- H2. *As an owner, I want nobody else to be able to take over my freshly installed instance.* ✔ The initial setup screen requires a one-time install code that only appears in the container logs.
- H3. *As a non-technical owner, I want to connect Claude without understanding MCP.* ✔ The welcome page offers, depending on the client: the URL to paste in "Add connector" (claude.ai / Desktop) or a prompt/command that Claude Code runs by itself. A "Test connection" button confirms the agent has already called the server.

**Agent**
- H4. *As an agent, I want to know how to write a valid slide before writing it.* ✔ `get_authoring_guide` returns the format, limits and an example in < 2,500 tokens.
- H5. *As an agent, I want errors that tell me exactly what to fix.* ✔ Every error carries `code`, `message`, `path` (e.g. `slides[3].html`) and `hint`.
- H6. *As an owner, I want to be able to undo what the agent did.* ✔ Every change creates a revision; deletion goes to trash for 30 days.

**Presenting**
- H7. *As a presenter, I want the presentation to continue if the network drops.* ✔ With the presentation open, cutting the network does not interrupt navigation, steps, notes, clock or overview (automated test).
- H8. *As a presenter, I want to see notes and clock without the audience seeing them.* ✔ Presenter view in a separate window: current slide, next, notes, clock and target time.
- H9. *As a presenter, I want to use an ordinary Bluetooth clicker.* ✔ The keys emitted by HID presenters (PageUp/PageDown, arrows, `b`/`.`, F5/Esc) work.

**Remote**
- H10. *As a presenter, I want to pair my phone in under 10 s.* ✔ `R` → QR → the phone controls; the laptop shows "Phone connected".
- H11. *As a presenter, I do not want someone in the audience to take control.* ✔ The QR is single-use and expires; a second device requires confirmation on the laptop.

**Sharing**
- H12. *As an owner, I want a read-only link that I can revoke.* ✔ Create, list, set expiry and revoke links; the link shows neither notes nor instance data.

**Audience**
- H13. *As an owner, I want to review the quiz before the audience sees it.* ✔ A quiz created by the agent stays as `draft` and cannot be launched until a human with a session approves it.
- H14. *As an attendee, I want to take part without installing anything or registering.* ✔ Scan QR → (nickname for the quiz) → participate; the page weighs < 60 KB compressed.
- H15. *As a presenter, I want offensive questions not to reach the projector.* ✔ The projector only shows questions when the presenter opens the view; they can hide/delete; there are rate limits and a basic filter.

## 5. v1 scope: validated and adjusted

I validate the proposed scope with **four adjustments** and one **reordering**. Full reasons are in the ADRs (`03-stack-and-adrs.md`).

### Included

| # | Capability | Adjustment vs. the proposal |
|---|---|---|
| 1 | Self-hosted server, one container, SQLite + files behind interfaces | No change |
| 2 | MCP server over **Streamable HTTP** at `/mcp`, 12 tools | **Adjustment A**: two ways to authenticate the agent: API token (Claude Code, from day 1) and built-in OAuth 2.1 (needed for claude.ai / Desktop / mobile). See §6 |
| 3 | Player: navigation, steps, notes, clock, overview, full screen, offline | **Adjustment B**: offline cannot depend only on the *service worker* (it does not exist on local-network `http://`). It is guaranteed by loading everything in memory; the service worker is an improvement when HTTPS is available. **Export to a single HTML file** is added as a universal plan B |
| 4 | Remote control: clicker, QR, laser pointer, same WiFi without internet | **Adjustment C**: Bluetooth between browsers is **not viable** (ADR-007). We do support physical Bluetooth clickers (they are keyboards) |
| 5 | Read-only public link, revocable and expiring | No change |
| 6a | Anonymous questions with votes | **Reordered**: goes before the quiz (it is simpler and validates the module contract) |
| 6b | Kahoot-style quiz with draft and approval | No change |
| 7 | One administrator, tokens with scopes, anonymous audience | No change |
| + | **Revisions and trash** | **Adjustment D (added)**: essential when the editor is an agent |
| + | Presentation export/import (`.pkn`) and instance backup | Added: it is the portability seam with the cloud |

### Out of v1 (but with the door open in the design)

| Topic | When | How the door stays open |
|---|---|---|
| Slide mirror on the phone, lock-screen controls | v1.1 | The real-time protocol already carries slide/step state; the remote renders the same document |
| `.mcpb` desktop package / stdio bridge for private-network instances | v1.1 | MCP lives in a package (`@pptaken/mcp`) independent of transport |
| The agent controls the presentation live | v2 | Session command bus with actor `agent` and scope `live:control` already reserved |
| Scripts in slides (interactive demos) | v1.x, off by default | The content already runs in an isolated iframe; it is a switch, not a redesign |
| Visual editor, teams, billing, marketplace | v2+ / cloud | Multi-tenancy possible: all tables carry `workspace_id` from day 1 |
| Third-party audience modules (plugins) | v2 | Stable module contract; in v1 only modules from the repo itself |
| Automatic security-focused PR review | Post-1.0 | See open-source guide §12 |

## 6. Reality of connecting with Claude (verified on 2026-11-12)

This conditions the product and the founder must know it:

- **claude.ai, Claude Desktop and the mobile app** connect to a custom connector **from Anthropic's cloud**, not from the user's machine. Therefore the instance must be **publicly reachable over HTTPS**. A server at `192.168.x.x` or `localhost` does not work for these clients. (Source: Claude connector documentation.)
- The generally supported authentication in those clients is **OAuth** (or none). Fixed headers such as `Authorization: Bearer` are in beta and only for some organizations. That is why PPTaken ships its own minimal OAuth server.
- **Claude Code** runs on the user's machine: it reaches `localhost` and the local network, and accepts a token header (`claude mcp add --transport http ... --header`). It is the simplest path and the first one we will build.
- Anthropic's "MCP tunnels" (for private-network servers) are a preview for Enterprise only: they do not serve our user.

Product consequence:

| Where PPTaken runs | Claude Code | claude.ai / Desktop / mobile | Present and remote |
|---|---|---|---|
| VPS with domain and HTTPS | ✔ | ✔ | ✔ (remote and audience need internet in the room) |
| PC or mini-server on the local network | ✔ | ✘ (v1.1: `.mcpb` desktop extension) | ✔ without internet |
| Presenter's laptop (Docker Desktop) | ✔ | ✘ | ✔; the phone connects to the laptop's hotspot |

The "executive who uses Claude in the browser" profile needs, when self-hosting, a server with a domain. That friction is exactly what `pptaken-cloud` will solve, and it is honest to say so in the documentation.

## 7. Onboarding flow (design)

```
[1] Terminal:  docker compose up -d            (or a one-line docker run)
[2] Logs:      "PPTaken ready at http://<host>:8080 · Install code: 7K2M-9QXD"
[3] Browser:   /welcome → asks for the code + create the owner's password
[4] "Connect your agent" screen with three tabs:
      ┌ Claude (web / desktop / mobile) ───────────────────────────────┐
      │ 1. Copy this URL:  https://slides.mydomain.com/mcp     [Copy]   │
      │ 2. In Claude: Customize → Connectors → Add → Custom             │
      │ 3. Paste the URL, leave what is marked "Detected", press Connect│
      │ 4. This instance will open so you can authorize Claude          │
      │ (warning if the instance is not public HTTPS: "use Claude Code  │
      │  or publish your server; guide →")                              │
      ├ Claude Code ───────────────────────────────────────────────────┤
      │ [Copy setup prompt]                                             │
      │ The prompt asks Claude Code to run `claude mcp add ...`         │
      │ with a freshly created token, verify with `whoami` and confirm.│
      ├ Other MCP client ──────────────────────────────────────────────┤
      │ URL + token + example JSON                                      │
      └─────────────────────────────────────────────────────────────────┘
[5] "Waiting for your agent's first call…" → ✔ "Claude connected"
[6] [Copy example prompt]: "Create a 5-slide presentation about…"
```

Important nuance about the **"Copy setup prompt"** button: in Claude Code the agent has a terminal and can configure itself, so the prompt works literally. In claude.ai the model **cannot add connectors to itself**: the user does it in Settings. There the button copies the URL and the page guides the 4 clicks. Promising otherwise would be a bad first impression.

Design details:
- The token included in the Claude Code prompt is created when the button is pressed, is shown once and is born with minimal scopes (`decks:read decks:write quiz:draft`).
- The prompt says to store the token in an environment variable or in Claude Code's user scope, not in a `.mcp.json` that ends up in git.
- The welcome page detects whether the public URL is HTTPS and adapts the messages.
- The whole interface in Spanish and English from day one.

## 8. Non-functional requirements (targets, not measurements)

| Requirement | v1 target |
|---|---|
| Footprint | Image < 150 MB compressed; idle RAM < 120 MB; runs on a 512 MB VPS |
| Startup | < 3 s to `/healthz` |
| Player | Slide change < 50 ms perceived; 60 fps transitions on an average laptop |
| Remote | Click→slide latency < 150 ms on LAN |
| Audience | 300 simultaneous participants on a 1 vCPU node (target to validate with a load test) |
| Sizes | Presentation ≤ 200 slides and ≤ 100 MB with assets; asset ≤ 10 MB (configurable) |
| Accessibility | Panels and audience pages WCAG 2.2 AA; full keyboard navigation |
| Browsers | Last 2 versions of Chrome, Edge, Firefox and Safari (incl. iOS) |
| Languages | es, en |
| Privacy | No telemetry by default. No external resources: nothing is requested from CDNs |
